A job's tags reach its runs, not only its notify hooks.

```
crontinental upgrade
```

No schema change; existing ledgers carry on as they are.

- **Tags in every run.** A job's command now gets its tags in the same
  variables its hooks do: `CRONTINENTAL_TAG_<KEY>=<value>` for each, and
  `CRONTINENTAL_TAGS` with the whole set as one JSON object (`{}` for none), so
  a tool the job calls can route by the booking without being told twice. A
  run gets the tags as they were when it started. Like `CRONTINENTAL_JOB`,
  `_RUN`, `_NEXT` and `_UNTIL` (all unchanged), none is inherited from a run
  that started this one, or from the service manager's environment: a
  `CRONTINENTAL_TAG_*` you set there yourself no longer reaches a run.
- **Hooks get `CRONTINENTAL_TAGS` too,** holding the event's tags (the job's,
  with a message's own `--tag` laid over them).
- **New tags are kept small and textual.** A value holds up to 1KiB of UTF-8
  (no NUL), and a job's set up to 8KiB as JSON (`&`, `<`, `>` count as one
  byte); more is refused at `--tag`, since every run carries them in its
  environment. A `notify --tag` inside a run is measured with the job's tags.
  Tags booked before this release are passed on as they always were; only one
  that cannot be a variable at all is left out, with a line in the log.
- **An unreadable tags column no longer stops anything.** It is taken as no
  tags, with a line on stderr, so a run still starts and `edit --tag` can write
  a good one over it.
- **A tags-only `edit` is now guarded** inside a Claude Code session, like any
  other edit of a job the session didn't book (`--force` when the user named
  it). Tags now change what a job's runs see. `--note` and `--notify` are still
  let through.
- **Tags are labels, never secrets.** They are plain in the ledger, the message
  book, `show`, `list --json` and every run's and hook's environment; the docs
  now say so.
