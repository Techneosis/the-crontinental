Each job says what it is doing, and a run that died without finishing is
written down as lost.

```
crontinental upgrade
```

No schema change.

- **`state` and `running` in `list --json` and `show --json`.** `state` is one
  word: `running`, `paused`, `failed`, `done` or `scheduled`. `running` is the
  run in progress (`{run, started_at, elapsed_sec}`) or null. A run counts as
  running only while the platform agrees it is alive (its systemd unit is up
  on Linux; on macOS the exec named in its lock file is still that job's
  exec), not just because the ledger says so. A run still going after
  `disable` reads `running`, and `enabled` says it won't go again. Runs that
  never started (`skipped`, `overlap`) are passed over.
- **`lost`, a new run outcome.** When a machine loses power mid-run, or the
  process recording a run is killed too hard to write its ending, the run used
  to stay `running` in the ledger for good. Now the tick checks each one more
  than a minute old, and one whose process is gone becomes `lost` (detail: "its
  run died without finishing"), once. It is reported to the notify hooks as a
  new `lost` event, critical, unless `--notify never`, all of a round's lost
  runs at once. The job reads `failed` until a run ends well. `list` marks it
  `LOST`, even behind the `skipped` a power cut with `catchup=skip` leaves.
- **The tick still never waits on a job.** The look-in on running runs comes
  after everything due has been dispatched, each process check is capped at
  3s (no answer: the ledger is believed), and a round with nothing lost stays
  at milliseconds.
- If your own hooks or tools read `outcome` or `CRONTINENTAL_EVENT`, `lost` is
  a new value of each; treat it like `killed`.
