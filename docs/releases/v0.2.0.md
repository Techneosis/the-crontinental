Notifications go where you want them, jobs can speak for themselves, and "now"
means now.

```
curl -fsSL https://raw.githubusercontent.com/Techneosis/crontinental/main/install.sh | bash
```

Running the one-liner again upgrades. The ledger is unchanged, so existing jobs
carry on as they were.

- **Notifications are hooks.** The binary decides *when* to notify (`--notify
  never|fail|always`, as before); the executables in
  `~/.config/crontinental/notify.d/` decide *where*. Each gets the event as
  `CRONTINENTAL_*` variables and as JSON on stdin, and a hook that fails or
  hangs never changes a run's outcome. The installer adds a `desktop` hook, so
  upgrading keeps your desktop notifications; delete it for none, or add
  others beside it. `notify/examples/` has [ntfy](https://ntfy.sh), for your
  phone, and a webhook. `show <name>` says where a job's notifications go, or
  that nobody is told.
- **`crontinental notify`.** A job can send its own message at any point, as
  itself: `crontinental notify "disk is 91% full"`, with `--urgent` and
  `--title`. It goes out whatever `--notify` says, so `--notify never` plus a
  message of your own is quiet unless it matters. It works from any script,
  too.
- **Start now.** `in 0` and `at now` run a one-off straight away instead of on
  the next tick, and `every … --now` adds one run at once without moving the
  schedule. `edit <name> --in 0` brings a waiting one-off forward to now.

Fixes:

- A time with a zone (`at "10:00 UTC"`) could land a day off when the UTC date
  and the local one differed. It now follows GNU `date`: the date comes from
  local time, and only the time is read in the zone.
- On Linux, a run stopped at its timeout could be recorded as `fail -15`
  instead of `killed`, and notified twice, when its job had notifications on
  (the default). A run now has exactly one ending.
